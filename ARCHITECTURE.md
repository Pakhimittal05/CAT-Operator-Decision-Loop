# CAT Operator Decision Loop — Technical Architecture

## 1. Technology Stack

| Layer | Choice | Rationale |
|---|---|---|
| Backend | Python 3.11, FastAPI | Async, auto OpenAPI docs, fast to build for a hackathon |
| ML | scikit-learn (GradientBoosting/RandomForest), NumPy, pandas | Interpretable, no GPU needed, fast train/infer |
| DB | SQLite (via SQLAlchemy) | Zero-config, file-based, portable, sufficient for synthetic scale |
| Frontend | React + Vite, Tailwind, Recharts | Fast to build dashboards/charts; team likely already knows React |
| Task scheduling | Simple Python scripts / FastAPI background tasks | No need for Celery/Kafka at hackathon scale |
| Packaging | Single repo, `uvicorn` + `npm run dev`, optional `docker-compose` for judges | Local-only requirement |

No microservices — one FastAPI app, one SQLite file, one SPA. No LLM anywhere in the core intelligence (per AI principle); an LLM is *optional* only for generating human-readable coaching text templates, and even that can be done with string templates instead.

---

## 2. Frontend Architecture

Single-page React app with five views mapped directly to the product's three uses + decision loop:

- **Dashboard** — daily tasks, safety compliance widgets, incident feed
- **Operator Profile** — dynamic performance state, deviation trends per dimension
- **Anomaly/Coaching Feed** — anomaly events, probable contributing dimensions, recommended training
- **What-If Simulator** — operator/machine/task/weather selectors → predicted outcome with uncertainty band
- **Predicted vs Actual** — post-task comparison view, the centerpiece demo screen

State managed with React Query (server state) + minimal local state. All charts (deviation radar, time-series, predicted-vs-actual bars) via Recharts. A persistent "Synthetic Data" banner appears on every screen.

---

## 3. Backend Architecture

FastAPI app organized by domain, not by technical layer, so each folder mirrors the pipeline stage (see directory tree). Core internal module: `deviation_engine` — a pure-Python/pandas library callable from three contexts (state update, anomaly check, simulation), so the "shared intelligence" requirement is enforced structurally, not just conceptually. All ML models loaded once at startup (`joblib`), reused across requests.

Request flow for the core loop:
```
Client → FastAPI router → Service layer (business logic) → Deviation/Prediction engine → DB (SQLAlchemy) → Response
```

---

## 4. Database

SQLite, single file, WAL mode for concurrent read/write during demo. All tables timestamped and tagged `is_synthetic BOOLEAN DEFAULT TRUE`.

---

## 5. Synthetic Data Generator

A standalone script (`generate_historical_data.py`) producing the **training corpus** using **Stochastic Process A**:
- Operators (n≈30) with latent skill parameters (efficiency_mean, idle_tendency, safety_tendency) drawn from distributions per skill tier.
- Machines (n≈10) with age-based wear factors.
- Tasks (n≈8 types) with baseline expected duration/load-cycle profiles.
- Weather sampled from categorical distribution affecting duration/risk multipliers.
- Historical task instances (n≈3000+) generated by combining operator latent skill + machine wear + task baseline + weather multiplier + Gaussian noise + occasional safety-event injection (Bernoulli, probability modulated by safety_tendency and fatigue proxy).

A **separate script** (`generate_actual_outcomes.py`) implements **Stochastic Process B** for "live/demo" task outcomes: different noise distribution (e.g., log-normal duration noise vs. Process A's Gaussian), different hidden variation (a small random daily "operator fatigue/mood" factor not present in Process A), and different safety-event trigger logic (threshold-based rather than probability-based). This script's exact formula is **not** imported into the ML training pipeline — enforced by keeping the two generators in separate modules with no shared random seed or shared parameter file, only shared *schema*.

## 6–8. ML Models, Training/Inference Flow, Deviation Vector

### Deviation Vector D(telemetry, context, reference)

For a task instance, compute a **reference profile** = expected performance for (task_type, machine_age_bucket, weather) using historical percentiles/regression fit (not the same operator's own history — a global reference model). Deviation is a vector of standardized (z-score-like) differences across 5 dimensions:

```
D = [d_cycle_efficiency, d_idling, d_duration, d_load_cycle, d_safety]
d_i = (observed_i - reference_mean_i) / reference_std_i
```

This is computed by a single function `compute_deviation()`, called identically by the state updater, the anomaly detector, and the simulator's post-hoc comparison — this is the "shared evidence-based" core.

| Component | Spec |
|---|---|
| **INPUT** | task telemetry (duration, idle_seconds, load_cycles, efficiency_score, safety_flags), task context (task_type, machine_id, weather) |
| **OUTPUT** | 5-dim deviation vector + composite deviation magnitude |
| **MODEL** | Reference profile = **Gradient Boosting Regressor** (per dimension) trained to predict "expected" value given (task_type, machine_age, weather); deviation = residual standardization using historical std per (task_type, weather) bucket |
| **TRAINING DATA** | Historical synthetic dataset (Process A) |
| **INFERENCE DATA** | Any task instance (historical, live demo, or simulated) |
| **EVALUATION METRIC** | Reference model MAE/RMSE per dimension against held-out historical data; deviation calibration checked via % of historical points falling in expected z-ranges |

---

## 9. Operator State Calculation

Aggregates deviation vectors over an operator's task history with **exponentially weighted moving average (EWMA)**, recency-weighted, per task-type and overall.

| Component | Spec |
|---|---|
| **INPUT** | Sequence of an operator's deviation vectors over time, task types |
| **OUTPUT** | Dynamic Operator State: per-dimension skill scores (continuous 0–100), overall composite score, trend direction, confidence (based on sample count) |
| **MODEL** | Deterministic statistical aggregation (EWMA, not a trained model) — chosen for explainability and because it must update incrementally after every task |
| **TRAINING DATA** | N/A (rule-based aggregation) |
| **INFERENCE DATA** | Operator's deviation history |
| **EVALUATION METRIC** | Stability check (state doesn't oscillate wildly on single outlier task); backtest correlation between state and known latent skill tier used in generator (internal validation only, never shown to judges as "ground truth") |

State replaces the static Expert/Intermediate/Beginner label but a **derived label** is still shown for UI legibility, computed from thresholds on the composite score.

---

## 10. Task-Time Prediction

| Component | Spec |
|---|---|
| **INPUT** | operator_id (→ operator state features), machine_id (age, type), task_type, weather |
| **OUTPUT** | predicted duration (point estimate) + uncertainty interval (P10–P90) |
| **MODEL** | **Gradient Boosting Regressor** for point estimate; **Quantile Gradient Boosting** (or NGBoost/simple residual-bootstrap) for uncertainty bounds |
| **TRAINING DATA** | Historical synthetic dataset (Process A) — features include operator's *historical* deviation-derived skill scores at time of task, not future info |
| **INFERENCE DATA** | Current operator state + selected machine/task/weather (used both for real upcoming tasks and what-if simulation) |
| **EVALUATION METRIC** | MAE, RMSE on held-out historical split; prediction interval coverage (% actuals falling within P10–P90) |

---

## 11. Risk/Anomaly Detection

Two-part: (a) **statistical anomaly on deviation vector** — flag when composite deviation magnitude exceeds a threshold (e.g., >2σ) relative to the operator's own rolling baseline; (b) **probable attribution** — rank the 5 dimensions by contribution to the anomaly (largest |z| first), reported as "probable contributing factors" with confidence, never causal language.

| Component | Spec |
|---|---|
| **INPUT** | Live/new deviation vector, operator's historical deviation distribution |
| **OUTPUT** | Anomaly flag (bool), severity score, ranked probable contributing dimensions with confidence %, skill-gap flag → training recommendation trigger |
| **MODEL** | Rule/threshold-based on deviation z-scores (Isolation Forest optional as a secondary cross-check, trained on historical deviation vectors) |
| **TRAINING DATA** | Historical deviation vectors (Process A) for baseline distribution / Isolation Forest fit |
| **INFERENCE DATA** | Latest task's deviation vector |
| **EVALUATION METRIC** | Precision/recall against synthetically injected anomalies in Process A holdout (generator knows which rows were injected as anomalous) |

---

## 12. What-If Simulation

Reuses the **Task-Time Prediction model** and **Deviation reference model** directly — this is the "same shared intelligence" requirement satisfied structurally.

Flow: manager selects operator + machine + task + weather → system computes:
- expected completion time + uncertainty (from prediction model)
- skill fit (operator's stored state score for that task_type vs. task difficulty baseline)
- behavioral/safety risk indicator (probability derived from operator's historical safety-dimension deviation + task/weather risk multiplier — logistic regression or simple weighted rule)
- training recommendation if skill fit below threshold

After actual task execution (via Process B), the **same deviation engine** computes actual deviation, and a comparison view shows predicted vs. actual with error, which feeds back into operator state update.

| Component | Spec |
|---|---|
| **INPUT** | Hypothetical (operator, machine, task, weather) combination |
| **OUTPUT** | Predicted duration+uncertainty, skill fit score, safety risk %, training flag |
| **MODEL** | Same GB regressor + logistic risk model as above (no separate model) |
| **TRAINING DATA** | Process A |
| **INFERENCE DATA** | Manager-selected hypothetical combination |
| **EVALUATION METRIC** | N/A at simulation time; validated post-hoc via predicted-vs-actual comparison once Process B outcome is recorded |

---

## 13. Safety-Event Engine

**Explicit, rule-based, not ML.** Two independent detectors:
- **Seatbelt**: telemetry field `seatbelt_engaged` (bool per time-slice); event triggered if unengaged while machine in motion/operating for > threshold seconds.
- **Proximity hazard**: telemetry field `min_proximity_distance`; event triggered if below configured safe distance for the zone/machine type.

Both write directly to a unified `incident_events` table alongside anomaly-detector-generated events and manually logged incidents, distinguished by `source` field (`seatbelt`, `proximity`, `deviation_anomaly`, `manual`). This satisfies "safety events must enter the common incident/event timeline" while keeping them architecturally separate from the deviation model.

---

## 14. Training Engine

Rule-based recommendation mapping: for each deviation dimension flagged as a skill gap (persistent negative deviation in operator state, not just one-off), map to a corresponding e-learning module (deterministic lookup table, demo content) and offer instructor booking. Instructor booking is a working local CRUD workflow (available slots table, booking table) — no external calendar integration needed.

---

## 15. Feedback / Recalibration

Closed loop: after Process B generates actual telemetry for a simulated/assigned task → deviation engine computes actual deviation → compared against the prediction made earlier (stored at simulation time) → error metrics stored → operator state EWMA updated with new deviation vector → UI shows predicted-vs-actual delta. This is the single most important demo screen and must be wired first.

## 19. Testing Strategy

- **Unit tests**: deviation calculation correctness (known input → known z-scores), operator state EWMA math, safety threshold rules.
- **Data validation tests**: generator output ranges (no negative durations, valid categorical values), schema conformance.
- **Model tests**: prediction MAE below a fixed threshold on holdout Process A split; anomaly detector precision/recall on injected anomalies.
- **Integration test**: full loop — simulate → predict → generate actual (Process B) → feedback update → assert state changed as expected direction.
- Use `pytest`, run against a temp SQLite DB fixture.

---

## 20. Demo Mode

A `seed_demo.py` script resets DB, loads a curated small set of operators/machines/tasks with pre-generated interesting history (one clearly-skilled operator, one with a known idling pattern, one with a near-miss safety event) so the 5-minute demo is reliable and not randomly boring. A visible "Synthetic Data — Hackathon Demo" watermark/banner is hardcoded into the frontend shell.

---

## 21. Local Deployment

`docker-compose.yml` optional (backend + static frontend build) or simply: `pip install -r requirements.txt && uvicorn app.main:app`, `npm install && npm run build`. README with one-command setup script `./setup_and_run.sh`. No cloud dependency, no external API keys required.

---

## 22. Error Handling

FastAPI exception handlers for validation errors (422), not-found (404), model-not-loaded (503 with clear message at startup if `models/*.joblib` missing — instructs user to run training script). Frontend shows toast notifications, never blank-screens on API failure.

---

## 23. Data Validation

Pydantic schemas for every API input/output. Generator-side validation: assert no NaNs, durations > 0, proximity distances ≥ 0, categorical fields within allowed enum sets, before writing to DB.

---

## 24. Model Explainability

Since GradientBoosting is used, expose per-prediction **feature importances** (global) and for individual predictions, simple **contribution breakdown** (e.g., via built-in feature_importances_ or a lightweight SHAP if time allows, else manual delta-from-mean breakdown) shown in the UI as "why this prediction" — always phrased as "probable contributing factors," "confidence: X%," never "caused by."

# D. ML PIPELINE

```
generate_historical_data.py (Process A) 
  → train reference_model.py, task_time_model.py, risk_model.py, isolation_forest(optional)
  → save to /models/*.joblib
  → runtime: deviation.py + operator_state EWMA + anomaly/detector.py + simulation/whatif.py
      all consume the same loaded models
  → generate_actual_outcomes.py (Process B, independent) produces "actual" telemetry
  → compare predicted vs actual → feedback updates operator_state
```

6. Anomaly detection + training recommendations
7. Process B generator + predicted-vs-actual feedback loop
8. Demo seed data + polish + explainability UI

# F. 5-MINUTE DEMO FLOW

1. (0:30) Dashboard: daily tasks, safety compliance, synthetic-data banner.
2. (1:00) Operator profile: dynamic state (not static label), deviation trend.
3. (1:30) Anomaly feed: flagged event, probable contributing dimensions, confidence.
4. (1:30) What-if simulator: pick operator/machine/task/weather → predicted time + uncertainty + risk + training flag.
5. (1:30) Trigger actual outcome (Process B) → predicted-vs-actual comparison → operator state updates live. This closes UNDERSTAND → SIMULATE → DECIDE → ACT → LEARN in front of the judges.
